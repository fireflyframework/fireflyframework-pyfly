# Function sandbox

`pyfly.agentic.sandbox` provides a trusted controller for JSON-in/JSON-out Python functions running in an isolated OCI container. Source runs only in the container. The Docker backend requires an explicitly selected daemon and an operator-approved runner image pinned by SHA-256 digest. The image recipe is in `sandbox-image/Dockerfile` and must be built and distributed by the operator.

Construct `FunctionSandbox(DockerSandboxBackend())`, or use `RoutingSandboxBackend({"docker": DockerSandboxBackend()})` when composing backends. An immutable `SandboxProfile` records the approved image, Docker context and daemon ID; `FunctionInvocation` records the source digest, inputs and resource limits. Invoke with trusted asynchronous `authorize`, `observe` and optional `effects` callbacks. The observer must durably record the exact resource before source is sent. Authorization must enforce current caller and effect permissions, and the effects callback must keep credentials in the trusted controller.

The guest defines `main(inputs)` and may return JSON or an awaitable resolving to JSON. The injected `effect(name, args)` function uses a bounded framed channel to request a trusted callback. All guest frames are untrusted. The callback must enforce its own operation allowlist and durable idempotency. Do not put credentials or capabilities into guest inputs, results, images or environment.

The Docker backend creates a non-root, read-only, network-disabled container without capabilities, with a bounded temporary filesystem, memory and PID limits. It disables Docker container logging because the framed guest channel carries function data. The runner sets CPU, address-space and process resource limits. Linux `RLIMIT_NPROC` applies per real UID, not per pod; other processes with that UID can affect availability. These controls do not defend against a compromised kernel or container runtime. Protect the Docker daemon and restrict who may approve an image, context and profile.

Always inspect `FunctionOutcome.status` and `cleanup_confirmed`. `unknown` means creation, an external effect, or cleanup could not be confirmed. Do not automatically repeat an unknown invocation. Persist the observed `SandboxResource` and call `reconcile(profile, resource)` on recovery to attempt removal of that exact owned resource. A successful reconciliation confirms absence on the pinned daemon; a daemon identity mismatch or inaccessible daemon is not confirmation.

`PrelaunchRejected` is reserved for a known policy rejection before any resource creation attempt. The supervisor reports it as `failed` with `POLICY_REJECTED`, no resource and confirmed cleanup. A failed or cancelled create request remains unknown, including name collisions and ambiguous API responses.

`KubernetesSandboxBackend` is available with `pyfly[agentic-sandbox-kubernetes]`, which pins the official Kubernetes client. It requires a dedicated restricted namespace, a tested CNI deny-all policy and a trusted `verify_isolation(profile)` callback; the callback must fail closed if that evidence is missing or stale. A verifier using separate credentials must prove that both credentials resolve to the same trusted API server and TLS identity, not merely compare kubeconfig paths.

The required asynchronous `prepare_profile(profile, execution_id)` callback supplies a protected, immutable controller-configuration snapshot for that execution. It must preserve the approved profile identity, image, context and namespace, include any referenced credential and CA material, and be checked by the verifier. The required `release_profile(prepared_profile, execution_id)` callback disposes of the snapshot only after termination and exact-UID cleanup are confirmed. Retain snapshots after unknown creation or cleanup, and make preparation idempotent for recovery; the controller must protect them from modification and unauthorized reads.

The runner closes the original stdout and stderr descriptors before loading guest code. A single direct Kubernetes API websocket forwards a framed socket bound to pod loopback; no host listening port is created. The backend verifies the pod's UID and restricted specification after a challenge on that stream before delivering source. The input stream has a cumulative cap of 2 MiB plus the configured output limit, including frame headers; individual valid effect replies may therefore exceed the cumulative allowance when repeated. The Kubernetes invocation timeout is at most 30 seconds. The backend observes a terminal container state before deleting the pod with a UID precondition. A missing or unreachable pod is not evidence that its process stopped. Use a cleanup timeout long enough to observe the active deadline and termination; otherwise retain an unknown outcome and quarantine capacity for reconciliation. Kubernetes process limits use the guest's per-UID `RLIMIT_NPROC`; they are not a per-pod PID guarantee.
